一、MyBatis 是什么？

1.1 一句话定义

MyBatis 是一款半自动 ORM 持久层框架——你只需要写 SQL，它帮你把 Java 对象的属性值填进 SQL 参数位、把查询结果列自动映射回 Java 对象属性，省掉所有 JDBC 样板代码。

MyBatis 帮你做的事：

纯 JDBC 你要手写的 MyBatis 自动完成的
获取 / 关闭 Connection 连接池管理，自动获取和释放
PreparedStatement 设置参数 #{} 自动填值
ResultSet 遍历取值 resultType / resultMap 自动映射
异常处理 try-catch-finally 包装成 RuntimeException，不用强制 catch
SQL 字符串拼接（条件查询） 动态 SQL 标签自动拼装

1.3 半自动 ORM vs 全自动 ORM

  • 全自动 ORM（Hibernate）：写好实体类映射后，连 SQL 都不用写，框架自动生成。好处是省事，坏处是 SQL 不可控、复杂查询性能差。
  • 半自动 ORM（MyBatis）：SQL 你自己写，框架帮你传参、映射结果。SQL 可精细优化，灵活度极高。

打个比方：全自动 ORM 像自动挡汽车——踩油门就走，但你没法手动换挡；半自动 ORM 像手自一体——平时自动挡够用，想飙车时随时切手动。

1.4 ORM 映射关系

ORM（Object-Relational Mapping）就是在「数据库表」和「Java 类」之间建一座桥：

层面 数据库 Java
结构 表 sys_user 类 SysUser
字段 id、username Long id、String username
类型 bigint、varchar Long、String
关系 外键（表关联） 对象引用 / 集合

1.5 POJO 相关名词

名词 全称 用途
Entity Entity 与数据库表映射的类，一行数据 = 一个 Entity 对象
DTO Data Transfer Object 接口调用时传递参数用的对象
VO Value Object 给视图/表现层准备数据的对象
POJO Plain Old Java Object 普通老式 Java 对象，以上三者的统称

三、#{} 与 ${}：一字之差，天壤之别

这是 MyBatis 面试最高频的考点，也是实际开发最容易踩坑的地方。

3.1 #{}：预编译占位符（安全，推荐）

MyBatis 把 #{tigerId} 变成 JDBC 的 ? 占位符，再用 PreparedStatement.setXxx() 填值：

3.3 对比总结

对比项 #{} ${}
底层机制 PreparedStatement 的 ? 占位符 字符串直接拼接
SQL 注入 ✅ 安全 ❌ 有风险
性能 可复用预编译计划 每次重新解析 SQL
什么时候用 99% 的参数传值 动态表名 / 列名（JDBC 不允许 ? 替代表名）

口诀：能用 #{} 就用 #{}，只有表名 / 列名 / 排序方向等 JDBC 不接受 ? 的地方才用 ${}，而且一定要校验传入值。

四、数据输入：参数怎么传给 SQL？

4.1 单个简单类型

简单类型就是 int、Integer、String、Long 这些。

只有一个参数时，#{} 里的名字随便写，写 #{abc} 也能用——因为 MyBatis 只关心「第几个参数」，不关心名字。但为了可读性，还是写有意义的名字。

4.2 实体类类型

传入一个 Java 对象，MyBatis 根据 #{属性名} 反射调用 getXxx() 取值：

#{tigerName} → MyBatis 调用 tiger.getName() 取值。属性名必须和实体类的 get/set 方法名对应。

4.3 多个零散参数：@Param

参数不止一个、又不是同一个实体类的字段时，用 @Param 给每个参数起别名：

多参数时如果不加 @Param，MyBatis 默认用 param1、param2 做 key，XML 里得写 #{param1}、#{param2}，可读性极差。多参数场景强烈建议显式加 @Param。

4.4 Map 类型

参数多又没对应实体类时，可以塞进 Map：

#{} 里的名字 = Map 的 key。实际开发中如果参数超过 3 个，建议封装成实体类或 DTO，不要用 Map（可读性差、容易拼写错误、不好维护）。

五、数据输出：结果怎么拿回来？

5.1 增删改：返回受影响行数

insert / update / delete 标签的返回值就是受影响行数，不用指定 resultType。

5.2 查询：返回简单类型

MyBatis 内置了常用类型别名：int = Integer、string = String、long = Long、map = Map 等，不用写全类名。

5.3 查询：返回实体类对象

MyBatis 把每一列的值按「列名 → 属性名」映射，填进 Tiger 对象。开了驼峰映射后，tiger_id 列自动找 tigerId 属性。

5.4 查询：返回 List

注意 resultType 写的是实体类类型（单个元素的类型），不是 List！MyBatis 自动把多行结果封装成 List。

5.5 查询：返回 Map

没对应实体类、只想要零散几列时，用 Map 封装一行数据：

⚠️ Map 只能封装一行结果。查到多行会抛 TooManyResultsException。多行用 List<Map<String, Object>>。

5.6 自增主键回填（重点理解！）

新增后想拿到数据库生成的自增 ID，加两个属性就行：

关键理解：

  • useGeneratedKeys="true" → 告诉 MyBatis 去获取自增主键值
  • keyProperty="tigerId" → 告诉 MyBatis 把主键值填到对象的哪个属性

5.7 字段与属性不对应怎么办？

三种解决方案，从简单到复杂：

方案一：SQL 别名（最直白）

简单粗暴，但要每条 SQL 都写 AS。

方案二：全局驼峰映射（推荐，一劳永逸）

自动把 tiger_id → tigerId、create_time → createTime、role_id → roleId。一次配置，全局生效，99% 的场景够用了。

方案三：resultMap（复杂映射用）

列名和属性名差异大、或涉及多表关联时，用 resultMap 显式声明映射关系：

<id> 标签标识主键列（MyBatis 用它判断对象唯一性），<result> 标签标识普通列。resultMap 和 resultType 互斥，同一个 <select> 里只能用其中一个。

<where> 自动做两件事：

  2. 自动去掉内容开头多余的 AND / OR（你不用写 WHERE 1=1 了）

都不传 SELECT * FROM t_tiger（没有 WHERE 子句，查全部，不会报错）

6.4 set 标签

更新部分字段时，用 <set> 动态拼 SET 子句，自动去掉末尾多余逗号：

如果只传 tigerName，生成的 SQL 是 UPDATE t_tiger SET tiger_name = ? WHERE tiger_id = ?。末尾的逗号被 <set> 自动去掉了。

七、多表关联查询

这是 MyBatis 最强大的特性之一：用 resultMap 把多表 JOIN 的结果映射成带嵌套关系的 Java 对象。

7.1 场景说明

以客户（Customer）和订单（Order）为例：一个客户有多个订单，一个订单属于一个客户。

7.2 对一查询（association）

需求：查一个订单，同时带出它所属的客户信息。

记忆方式：对一用 <association>，属性 javaType 指定「关联的对象是什么类型」。

7.3 对多查询（collection）

需求：查一个客户，同时带出他名下的所有订单。

记忆方式：对多用 <collection>，属性 ofType 指定「集合里的元素是什么类型」。

7.4 关键词总结

关联类型 标签 关键属性 记忆口诀
对一 <association> javaType 「关联一个对象」→ 用 javaType 指定类型
对多 <collection> ofType 「关联一组对象」→ 用 ofType 指定元素类型

7.5 分步查询与延迟加载

为什么需要分步？

多表 JOIN 一次性查出所有数据，简单粗暴。但如果关联层级深（A→B→C→D），一条 SQL 会非常庞大、性能差。而且有些关联数据不一定每次都用得到。

分步查询：把一条 JOIN SQL 拆成多条独立 SQL，按需调用。

配置分步查询

MyBatis 执行 selectCustomerWithLazyOrders(1) 时：

  1. 先执行查客户的 SQL
  2. 拿到 customer_id = 1，传给分步 SQL selectOrdersByCustomerId(1) 查订单
  3. 把订单结果封装进 orderList

开启延迟加载

默认情况下分步查询是立即加载（两步一起执行）。开启延迟加载后，第二步只有在真正用到 orderList 时才执行：

延迟加载的好处：如果 100 次查客户中只有 15 次需要看订单，剩下 85 次就省掉了查订单的 SQL 开销。

8.5 XML 还是注解？怎么选？

对比 XML 方式 注解方式
适合场景 复杂 SQL、动态 SQL、多表关联 简单单表 CRUD
动态 SQL <if>/<where>/<foreach> 强大 需要拼接字符串或用 @SelectProvider（不方便）
可读性 SQL 和 Java 分离，清晰 SQL 写在注解里，长 SQL 很难看
维护性 改 SQL 不用动 Java 代码 改 SQL 要重新编译
实际开发 主流方式，95% 用 XML 简单查询偶尔用

建议：项目里统一用 XML 方式。注解方式了解一下就行，面试会问，实际开发很少用注解写复杂 SQL。

九、PageHelper 分页插件

分页是业务开发中最常见的需求之一：数据太多不能一次全查出来，要按页展示。PageHelper 是 MyBatis 最流行的分页插件，用起来非常简单。

9.1 为什么需要分页？

假设 sys_user 表有 10 万条数据，你不分页直接 SELECT * FROM sys_user，数据库要把 10 万条全查出来传给 Java——内存爆了、页面卡死、用户也看不过来。

分页就是：每次只查一页数据（比如每页 10 条），用户翻页时再查下一页。

手动算 LIMIT 偏移量也行，但每次都要再查一次 COUNT(*) 拿总条数，很麻烦。PageHelper 帮你自动搞定这两件事。

9.2 引入依赖

pagehelper-spring-boot-starter 是 PageHelper 整合 Spring Boot 的启动器，引入后自动配置，不用写配置类。

9.3 使用方式（三行代码搞定）

原理：PageHelper.startPage(1, 10) 会在当前线程里存一个分页参数。接下来你执行任何一条查询，PageHelper 的拦截器会自动在 SQL 末尾拼上 LIMIT 0, 10，同时再发一条 SELECT COUNT(*) 查总数。你完全不用改 SQL！

  1. startPage() 后必须紧跟一条查询：中间不能插其他代码，否则分页参数会作用到错误的查询上。
  2. 只对 MyBatis 查询生效：PageHelper 是 MyBatis 拦截器，只拦截 Mapper 方法的 SQL。
  3. 不要在 startPage() 后查多次：分页参数只用一次，第一条查询用完就清掉了。
