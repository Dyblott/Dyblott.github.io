框架核心原理讲解

本文系统讲解 Spring 框架的底层核心原理。前半部分聚焦 AOP 与声明式事务（日常开发最常用、也最容易踩坑的两块），后半部分讲解 IoC 容器层面的作用域、生命周期、循环依赖，以及 Spring MVC 的请求处理流程与设计模式应用。

第一部分：AOP 与声明式事务

1. AOP 面向切面编程思维

1.1 AOP 主要解决什么问题

AOP（Aspect Oriented Programming，面向切面编程）是对 OOP（面向对象编程）的补充，核心解决业务逻辑与非业务逻辑耦合、重复代码冗余的问题。

问题 1：非业务逻辑散落在业务代码中，耦合严重

场景：用户管理模块（UserService）的 login / saveUser / updateUserById 等方法都需要「权限校验」「事务控制」。

  • 无 AOP：需在每個业务方法内手动编写日志、权限、事务代码，业务方法既含核心逻辑又混杂非业务逻辑；
  • 有 AOP：将日志、权限、事务等“横切逻辑”抽离成独立的「切面」，无需修改业务方法代码，自动织入目标方法。

问题 2：重复代码冗余，维护成本高

场景：10 个 Service 的方法都要打印“方法入参 / 出参日志”。

  • 无 AOP：10 个 Service 的方法都重复写日志，改格式需逐个改；
  • 有 AOP：仅在切面写一次，通过“切入点”指定要增强的方法，所有目标方法自动复用。

核心价值总结：

无 AOP 的问题 AOP 的解决方案
业务与非业务逻辑耦合 抽离非业务逻辑为“切面”，与业务代码解耦
重复代码冗余 切面逻辑一次编写，多处复用
非业务逻辑修改需改动业务代码 仅修改切面，不影响核心业务代码

一句话：AOP 把业务代码里重复的非核心功能（如日志、事务）抽出来，在不改动业务代码的前提下动态加到目标方法里。

1.2 AOP 底层依赖的技术：代理模式

① 代理模式介绍

代理模式是 23 种设计模式之一，属于结构型模式。作用是通过代理类，在调用目标方法时间接调用，让非核心逻辑从目标方法中剥离出来——解耦。

生活中的代理例子：

  • 广告商找明星拍广告需经过经纪人；
  • 合作伙伴找老板谈合作需通过秘书；
  • 房产中介是买卖双方的代理。

相关术语：

  • 代理：封装非核心逻辑的类 / 对象 / 方法；
  • 目标：被“套用”了非核心逻辑的类 / 对象 / 方法，负责封装核心业务。

② 静态代理

生活案例：你有一套房子要出租，专门招了一个固定的中介，作为这套房子的专属代理，所有租房对接都由这个中介处理，他只服务你这一套房源。

静态代理确实解耦了，但代码写死了，完全不具备灵活性。其他地方也需要日志，还得再声明更多静态代理类，产生大量重复代码。

进一步需求：将日志功能集中到一个代理类中，用动态代理技术实现。

③ 动态代理

生活案例：你联系大型房产平台（如链家），不用管具体是谁来办事，平台会根据情况动态为你匹配最合适的中介，下次换房源可能分配另一个中介。你只对接平台，具体代理人员由平台按需生成——这就是动态代理。

动态代理是 AOP 的核心底层技术，与静态代理的核心区别：无需手动编写代理类，程序运行时由 JVM 自动生成代理类。一个通用增强逻辑可适配多个目标类，是 Spring AOP 的默认实现方式。

动态代理分两种：

  1. JDK 动态代理：基于接口实现，要求目标类实现至少一个接口；
  2. CGLIB 动态代理：基于继承实现，无需目标类实现接口。

JDK 动态代理（基于接口）

核心 API：java.lang.reflect.Proxy（生成代理对象）、InvocationHandler（定义增强逻辑）。

CGLIB 动态代理（基于继承）

核心 API：Enhancer（生成代理对象）、MethodInterceptor（定义增强逻辑）。无需目标类实现接口。

⚠️ Java 9+ 模块系统（JPMS）对反射做了严格限制。CGLIB 调用 ClassLoader.defineClass() 可能因未开放模块而报错：Unable to make protected final java.lang.Class java.lang.ClassLoader.defineClass(...) accessible。解决：添加 JVM 启动参数 --add-opens java.base/java.lang=ALL-UNNAMED。

动态代理核心总结：

特性 JDK 动态代理 CGLIB 动态代理
依赖条件 目标类必须实现接口 目标类无需实现接口
实现方式 实现与目标类相同的接口 继承目标类
核心 API Proxy + InvocationHandler Enhancer + MethodInterceptor
Spring AOP 适配 目标类有接口时默认使用 目标类无接口时自动切换使用

1.3 AOP 核心概念

AOP 利用横切技术，将分散在各处的非核心公共逻辑封装成独立可重用模块——切面（Aspect）。借助 AOP，可在不修改原有业务代码的前提下，将切面逻辑动态“织入”目标方法。

核心名词：

  • 横切关注点：从每个方法抽取出来的同一类非核心业务（如日志、事务、权限）。有十个附加功能，就有十个横切关注点。
  • 通知（增强）：横切关注点上要做的事情，写成方法即通知方法。
    • 前置通知：目标方法前执行；
    • 返回通知：目标方法成功结束后执行；
    • 异常通知：目标方法异常结束后执行；
    • 后置通知：目标方法最终结束后执行；
    • 环绕通知：用 try…catch…finally 围绕整个目标方法，包含上述所有位置。
  • 连接点（JoinPoint）：被拦截到的点，在 Spring 中是可被动态代理拦截的目标类方法。
  • 切入点（Pointcut）：定位连接点的表达式，如 execution(* com.example.service.impl.*.*(..))，符合条件的每个方法是一个具体连接点。
  • 切面（Aspect）：切入点和通知的结合，是一个类。
  • 目标（Target）：被代理的目标对象。
  • 代理（Proxy）：向目标应用通知后创建的代理对象。
  • 织入（Weave）：把通知应用到目标上，生成代理对象的过程。Spring 采用运行期织入。

Spring AOP 梳理：

  1. AOP 是区别于 OOP 的编程思维，解决非核心代码冗余和难维护问题；
  2. 代理技术（动态 / 静态）是实现 AOP 的具体技术，但自己写动态代理繁琐；
  3. Spring AOP 框架基于 AOP 思维，封装动态代理技术，我们只需写少量配置即可完成面向切面编程。

注：AspectJ 是早期 AOP 实现框架，Spring AOP 借用了 AspectJ 的 AOP 注解。

1.5 AOP 细节技术详解

① 获取目标细节信息（JoinPoint）

④ 切入点表达式语法

总体结构：execution([访问修饰符] [返回值] [包地址].[类名称].[方法名称]([参数]))

  • 第一位：execution() 固定开头；
  • 第二位：方法访问修饰符 public / private；
  • 第三位：方法返回值 int / String / void；
  • 第四位：包地址
    • 固定包：com.example.api
    • 单层任意：com.example.*
    • 任意层任意：com..（用在包上，.. 表示任意层任意命名）
  • 第五位：类名称
    • 固定：UserService
    • 任意类：*
    • 部分任意：com..service.impl.*Impl
  • 第六位：方法名称（语法同类名）
  • 第七位：方法参数
    • 具体：(String,int)（顺序敏感）
    • 无参：()
    • 模糊：(..) 任意参数（有或没有）
    • 部分：(String..) 第一个是字符串；(..String) 最后一个是字符串；(..int..) 包含 int 类型

切点表达式练习（参考答案）：

  1. 某包某类下，公有、返回 int 的全部方法：execution(public int com.example.service.UserService.*(..))
  2. 某包下类中第一个参数是 String 的方法：execution(* com.example.service.*.*(String..))
  3. 全部包下、无参数的方法：execution(* *..*.*())
  4. com 包下、以 int 参数结尾的方法：execution(* com..*.*(..int))
  5. 指定包下、Service 开头类的私有、返回 int、无参方法：execution(private int com.example.service.Service*.*())

2. 声明式事务注解

2.1 事务实现方式核心对比

  • 编程式事务：需开发者手动编写代码完成事务的开启、提交、回滚，事务逻辑与业务代码深度耦合；
  • 声明式事务：基于 Spring 框架，仅通过注解 / 配置“声明”事务规则，由框架自动管理，是开发主流方式。

2.2 声明式事务核心：@Transactional

@Transactional 是声明式事务的核心注解：

  • 作用范围：标记在类上 → 该类所有非私有方法应用事务；标记在方法上 → 仅当前方法（方法级优先级高于类级）；
  • 核心属性：
属性 说明
readOnly 只读事务，适用于查询场景，数据库可针对性优化
timeout 超时时长（秒），超时自动回滚，避免长期占用连接
rollbackFor / noRollbackFor 回滚 / 不回滚的异常类型（默认 RuntimeException）
isolation 隔离级别（读未提交 / 读已提交 / 可重复读 / 串行化）
propagation 传播行为（REQUIRED / REQUIRES_NEW 等）

2.3 传播行为解释

以下基于「方法 A（外层）调用方法 B（内层）」的嵌套场景说明。

案例 1：REQUIRED（默认值）— 共用一个事务

外层有事务则加入，无则新建。A、B 共用同一事务，要么一起提交，要么一起回滚。

结果：A、B 共用事务，抛异常 → 订单未创建，日志也未保存。

案例 2：REQUIRES_NEW — 新建独立事务

无论外层是否有事务，内层强制新建独立事务，提交 / 回滚与外层无关。

结果：

  • 内层 B 自己报错 → B 的独立事务立即回滚；A 是否回滚取决于是否捕获 B 的异常；
  • 外层 A 报错 → A 回滚，但 B 若已提交则不回滚（日志已保存，用于排查）。

第二部分：框架核心原理（IoC 容器与设计模式）

3. Spring 组件作用域

3.1 核心问题

Spring IoC 容器创建 Bean 时默认是单实例（整个容器仅一个实例）。

3.2 @Scope 注解控制作用域

  • singleton（默认）：单实例；
  • prototype：多实例，每次获取都创建新对象。

3.3 Bean 创建时机

  • 单例（singleton）：容器初始化阶段创建，仅一次；
  • 多例（prototype）：容器初始化完成后，每次 getBean() 时创建（延迟创建）。

核心总结：默认单例（容器启动时创建）；@Scope("prototype") 多实例（每次 getBean 新建）。

4. Spring 组件生命周期

4.1 理解生命周期的核心价值

Bean 从「创建 → 初始化 → 销毁」的完整过程，理解它有助于：

  1. 掌握实例化流程与配置特性；
  2. 利用扩展接口定制逻辑；
  3. 辅助理解 AOP、声明式事务的实现原理。

4.2 核心阶段

  1. 加载 Bean 定义：扫描注解，解析为 BeanDefinition 存储；
  2. 实例化 Bean：通过反射调用构造方法创建实例（仅创建，不赋值）；
  3. 设置属性：通过 @Autowired / @Value 注入依赖；
  4. 初始化方法（优先级：@PostConstruct > InitializingBean > 自定义 initMethod）；
  5. 就绪使用：Bean 可被引用调用；
  6. 销毁方法（仅单例，优先级：@PreDestroy > DisposableBean > 自定义 destroyMethod）。

4.3 自定义初始化 / 销毁方法（注解版）

4.4 生命周期扩展接口

接口 / 注解 作用
BeanFactoryPostProcessor 实例化前修改 BeanDefinition（如动态改属性）
BeanPostProcessor 初始化前后增强（AOP 核心扩展点）
BeanNameAware 获取 Bean 名称
ApplicationContextAware 获取容器上下文
@PostConstruct / @PreDestroy 替代 InitializingBean / DisposableBean

核心总结：注解版 @Component 替代 <bean>，@PostConstruct / @PreDestroy 替代 init-method / destroy-method；生命周期流程：加载定义 → 实例化 → 赋值 → 初始化 → 使用 → 销毁。

5. Spring 组件循环依赖与三级缓存

5.1 核心问题

当 Bean A、B 互相依赖注入时形成循环依赖。若通过构造器注入（public A(B b)），循环依赖无法解决（先有 A 还是先有 B 的死循环）。只有将「创建对象」与「设置属性」拆分为两步（无参构造创建空对象 + setter / 注解注入），Spring 才能通过三级缓存破解。

5.2 三级缓存机制

缓存级别 核心属性 作用
一级缓存 singletonObjects 存放完全初始化的成品 Bean
二级缓存 earlySingletonObjects 存放创建完成但未初始化的早期 Bean
三级缓存 singletonFactories 存放 Bean 工厂，生成早期引用

处理流程（A 依赖 B，B 依赖 A）：

  1. 创建 A 空对象 → 把 A 的工厂放入三级缓存；
  2. 为 A 注入 B → 创建 B 空对象 → 把 B 的工厂放入三级缓存；
  3. 为 B 注入 A → 从三级缓存取 A 的工厂生成早期引用，移入二级缓存，注入 B；
  4. B 完成初始化 → 移入一级缓存；
  5. 从一级缓存取 B 注入 A → A 完成初始化，移入一级缓存。

关键注意点：

  1. Spring 不推荐循环依赖，默认禁用，需开启 spring.main.allow-circular-references=true；
  2. 仅单例 Bean 支持循环依赖，原型（多实例）不支持；
  3. 构造器注入无法解决，仅支持 setter / 注解注入。

面试精简回答： Spring 通过三级缓存解决单例 Bean 循环依赖——一级存成品、二级存早期、三级存工厂；创建时先暴露早期引用打破死锁；注意构造器注入不支持，需无参构造 + 属性注入，且需手动开启开关。

6. AOP 原理与应用场景（底层实现）

6.1 AOP 与 Bean 生命周期的关联

Spring AOP 基于动态代理实现，核心增强逻辑嵌入在 Bean 生命周期中，关键节点是 BeanPostProcessor 的 postProcessAfterInitialization。

  • 触发时机：代理对象在 Bean 生命周期的「初始化后」阶段生成；
  • 代理方式：目标类实现接口 → JDK 动态代理；无接口 → CGLIB 代理；
  • 核心原理：扫描到切面类后，在 Bean 初始化完成时，对匹配切点的 Bean 生成代理对象，替换原 Bean 存入容器；调用方法时先执行代理增强逻辑，再执行原方法。

6.2 典型应用场景

① 日志记录

② 声明式事务（AOP 模拟）

③ 权限校验

④ 异常统一处理

核心总结：AOP 代理在 Bean 初始化后（BeanPostProcessor 后置阶段）生成；核心价值是解耦业务逻辑与通用逻辑；典型场景包括日志、事务、权限、异常处理、性能监控。

7. Spring 声明式事务失效场景

声明式事务基于 AOP 动态代理，所有失效场景本质都是代理机制未触发或事务规则不满足。

7.1 典型失效场景

场景 原因 错误示例
非 public 方法 事务 AOP 默认仅拦截 public 方法 @Transactional private void createOrder()
同类内部调用 内部调用走原对象，跳过代理 this.innerMethod()（innerMethod 有事务）
异常被捕获未抛出 事务无法感知异常 try { ... } catch (e) { print }
抛出受检异常未配 rollbackFor 默认仅回滚 RuntimeException @Transactional + throw new Exception()
传播属性错误 如 NOT_SUPPORTED 挂起事务 @Transactional(propagation = NOT_SUPPORTED)
类未被 Spring 管理 无代理对象 类无 @Service，手动 new
多线程 事务通过 ThreadLocal 绑定连接 子线程里操作数据库

7.2 避坑解决方案

失效场景 解决方案
非 public 方法 改为 public，或通过接口暴露（JDK 代理）
同类内部调用 注入自身代理调用 / 提取到新 Service / 用 AopContext 获取代理
异常被捕获 捕获后重新抛出（throw new RuntimeException(e)）
受检异常不回滚 配置 @Transactional(rollbackFor = Exception.class)
传播属性错误 使用默认 REQUIRED，或按业务选择
类未被管理 加 @Component / @Service，通过容器获取 Bean
多线程 子线程单独开事务，或改用消息队列

核心总结：事务失效本质是 AOP 代理未触发（内部调用、非 public）或事务规则不满足（异常吞掉、传播错误）；遵循 public 方法、异常抛出、Spring 管理 Bean 的规范即可避坑。

8. Spring 中涉及的设计模式

模式 核心思想 Spring 应用
单例模式 全局仅一个实例 Bean 默认 singleton，DefaultSingletonBeanRegistry 三级缓存 + 双检锁保证
工厂模式 封装对象创建 BeanFactory（简单工厂）、FactoryBean（工厂方法）、ApplicationContext（抽象工厂）
代理模式 增强目标对象 JDK 动态代理（JdkDynamicAopProxy）、CGLIB（CglibAopProxy），用于 AOP、事务
模板方法 算法骨架 + 可变步骤延迟子类 JdbcTemplate、RestTemplate、RedisTemplate
观察者模式 一对多依赖，事件通知 ApplicationEvent + ApplicationListener，如 ContextRefreshedEvent
适配器模式 接口转换兼容 HandlerAdapter（适配不同 Controller）、MethodBeforeAdviceAdapter（AOP 通知适配）
装饰器模式 动态添加功能 BeanWrapper、HttpServletRequestWrapper
策略模式 多算法运行时选择 Resource（不同资源加载）、TransactionDefinition（事务策略）

核心要点：Spring 设计模式围绕解耦、复用、扩展；高频模式（单例、工厂、代理）是理解 IoC/AOP 的关键；多数模式并非孤立使用（AOP 同时用到代理 + 模板方法 + 适配器）。

9. Spring MVC 核心组件和调用流程

9.1 核心组件

组件 核心职责
DispatcherServlet 前端控制器（入口），接收所有请求，协调各组件
HandlerMapping 映射 URL 到对应 Handler，返回 HandlerExecutionChain（含 Handler + 拦截器）
HandlerAdapter 适配器，适配不同类型 Handler，统一执行
Handler（Controller） 处理器，业务逻辑核心（@RequestMapping 方法）
ModelAndView 封装结果（Model 数据 + View 视图名）
ViewResolver 视图解析器，根据视图名解析为具体 View
HandlerInterceptor 拦截器，在请求前后插入自定义逻辑
ExceptionResolver 异常解析器，统一处理请求异常

9.2 核心调用流程

  1. 用户向 DispatcherServlet 发送 HTTP 请求；
  2. DispatcherServlet 调用 HandlerMapping，按 URL 匹配 Handler；
  3. HandlerMapping 返回 Handler 给 DispatcherServlet；
  4. DispatcherServlet 将 Handler 交给 HandlerAdapter 适配；
  5. HandlerAdapter 调用目标 Handler（再依次调用 Service、Dao）；
  6. Handler 处理完，将结果返回 HandlerAdapter；
  7. HandlerAdapter 将结果（ModelAndView）返回 DispatcherServlet；
  8. DispatcherServlet 调用 ViewResolver 解析视图名；
  9. ViewResolver 返回具体 View；
  10. DispatcherServlet 渲染视图并响应给用户。

特殊场景补充：

  • RESTful 接口：返回 JSON/XML 时，HandlerAdapter（如 RequestResponseBodyMethodProcessor）直接转响应体，跳过 ViewResolver；
  • 拦截器执行：preHandle 在 Handler 前、postHandle 在 ModelAndView 返回后、afterCompletion 在响应返回后触发；
  • 异常处理：由 ExceptionResolver 统一捕获。

核心总结：DispatcherServlet 作为“总指挥”协调各组件；HandlerMapping 解耦 URL 与方法、HandlerAdapter 适配处理器、ViewResolver 解耦视图；标准化流程支持灵活扩展。

本文总结

Spring 框架的核心原理围绕两条主线：

  1. IoC 容器：通过单例 / 多例作用域、完整的 Bean 生命周期、BeanPostProcessor 扩展点、三级缓存解决循环依赖，支撑起整个对象管理体系；
  2. AOP 与代理：基于 JDK 动态代理 / CGLIB，在 Bean 初始化后生成代理对象，实现无侵入的日志、事务、权限、异常处理增强。

结合声明式事务（传播行为 + 失效场景）、设计模式应用与 Spring MVC 调用流程，即可从“会用”上升到“理解为什么能这样用”。
