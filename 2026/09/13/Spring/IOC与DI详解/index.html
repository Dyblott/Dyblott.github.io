IOC 与 DI 详解

一、什么是 IOC（Inversion of Control，控制反转）

1. 传统方式的痛点

传统开发中，对象由程序员自己 new，对象之间的依赖自己维护：

问题：

  • 耦合度高：UserDaoImpl 一旦改变（如换成 UserDaoRedisImpl），所有 new 它的地方都要改。
  • 难以测试：无法方便地替换为 Mock 对象。
  • 对象生命周期由程序员管理，繁琐且易出错。

2. IOC 的核心思想

控制反转：把对象的创建、管理、销毁的控制权，从程序员手中反转交给 Spring 容器（IOC 容器）。

  • 控制：对象的创建权、生命周期管理权。
  • 反转：由”程序员主动 new”变为”容器被动创建并注入”。

3. IOC 容器

Spring 中 IOC 容器是 ApplicationContext（底层接口为 BeanFactory），负责：

  1. 根据配置（注解/XML/JavaConfig）创建 Bean
  2. 通过 DI 装配 Bean 之间的依赖
  3. 管理 Bean 的生命周期（初始化、销毁）
  4. 提供单例缓存（默认单例作用域）

二、什么是 DI（Dependency Injection，依赖注入）

DI 是 IOC 的具体实现方式：容器在创建对象时，自动把它依赖的对象注入进来。

关系：IOC 是思想（目标），DI 是手段（实现）。Spring 中说”IOC 容器”，实际做的事就是 DI。

三种注入方式

1. 构造器注入（推荐 ✅）

优点：依赖不可变（final）、不会为 null、便于单元测试、能及时发现循环依赖。

2. Setter 注入

适合可选依赖（依赖可以有默认值）。

3. 字段注入（不推荐 ⚠️，但常见）

缺点：无法声明 final、脱离容器无法测试、掩盖依赖关系、容易引发 NPE。
注意：@Autowired 本身不能用在 static 字段上。

三、DI 相关注解

注解 来源 说明
@Autowired Spring 按类型（byType）注入，配合 @Primary/@Qualifier 处理多个候选
@Qualifier("name") Spring 按名称指定注入哪个 Bean
@Primary Spring 多个同类型 Bean 时标记首选
@Resource JDK (JSR-250) 先按名称（byName）找，找不到再按类型找
@Value("${key}") Spring 注入配置文件中的值
@Lazy Spring 延迟注入，第一次使用时才创建 Bean

四、Bean 的声明与管理

1. 声明 Bean 的方式

注解 用途
@Component 通用组件
@Service 业务层
@Repository 持久层
@Controller / @RestController 表现层
@Configuration + @Bean 第三方类（无法修改源码时用配置类手动注册）
@Import 导入其他配置类

2. Bean 的作用域

作用域 说明
singleton（默认） 容器中只有一个实例
prototype 每次获取都创建新实例
request 每个 HTTP 请求一个实例（Web 环境）
session 每个 Session 一个实例（Web 环境）

六、IOC/DI 的优势总结

优势 说明
低耦合 对象依赖接口而非实现，面向接口编程
可测试 单元测试可轻松注入 Mock 对象
易维护 组件即插即用，替换实现无需修改使用方
生命周期托管 单例缓存、初始化/销毁回调由容器统一管理
是 AOP 的基础 Bean 都由容器管理，AOP 代理才能无缝织入（如 @Transactional）

七、常见面试题速答

  1. IOC 和 DI 的关系？ IOC 是控制反转的思想，DI 是实现 IOC 的手段（依赖注入）。
  2. @Autowired 和 @Resource 区别？ 前者是 Spring 提供、按类型注入；后者是 JDK 标准、默认按名称注入。
  3. 为什么推荐构造器注入？ 依赖不可变、非空保证、利于测试、可及早暴露循环依赖。
  4. Bean 默认是单例吗？线程安全吗？ 默认单例；若 Bean 含可变成员变量则存在线程安全问题，应避免有状态或改用 prototype。
  5. BeanFactory 和 ApplicationContext 区别？ BeanFactory 是基础容器（懒加载）；ApplicationContext 是其超集，提供事件、国际化、注解扫描等企业功能，启动时预创建单例 Bean。
