Spring AOP 详解

一句话先记住 AOP 是什么：把那些”每个方法都要写一遍、但又和业务本身没多大关系”的代码（日志、事务、权限、耗时统计……）抽出来，放到一个独立的类里统一管理，然后在程序运行时”悄悄”地把它加回到目标方法上——业务代码一行都不用改。

AOP是基于IOC容器，对程序功能进行功能扩展。

本文从”为什么需要 AOP”讲起，一路讲到能读懂、能上手写切面，中间所有示例都配有通俗解释。

1. 为什么需要 AOP

1.1 一个真实场景

假设你写了一个用户服务 UserService，里面有登录、新增用户、修改用户等方法：

需求来了：

  • 每个方法都要打印日志（谁在什么时候调用了、参数是什么）；
  • 每个方法都要开启事务 / 提交 / 回滚；
  • 每个方法都要做权限校验。

1.2 传统做法的三个痛点

痛点一：业务代码被”杂质”污染。

一眼看过去，真正属于”登录”的只有中间那一行，其余全是重复的配角。

痛点二：重复代码到处都是。

10 个 Service、100 个方法，就要把这套日志、事务、权限代码抄 100 遍。

痛点三：改一处，动全身。

某天日志格式要加个时间戳，你得挨个方法去改，漏一个就出 bug。

1.3 AOP 的解决思路

把这套”到处都要写、内容和业务无关、各方法高度雷同”的逻辑抽出来，单独放进一个类里：

核心价值一句话：业务逻辑与非业务逻辑解耦，重复逻辑一次编写、处处复用，修改只改切面，业务方法不受影响。

2. AOP 到底是个啥

AOP = Aspect Oriented Programming，面向切面编程，它是 OOP（面向对象编程）的补充，不是要取代 OOP。

  • OOP 是纵向的：用封装、继承、多态把一个个业务对象组织成层次结构，它擅长处理核心业务（一个订单该怎么创建、一个用户该怎么注册）。
  • AOP 是横向的：它擅长处理横切的公共逻辑（日志、事务、权限、缓存、异常处理、耗时统计……）。
对比维度 OOP AOP
关注方向 纵向（类的层次） 横向（跨多个方法）
解决的问题 业务模块的组织与复用 公共逻辑的抽取与复用
典型场景 订单、用户、商品建模 日志、事务、权限、监控
关系 基础 补充完善

打个比方：一栋楼里每一户都要装水表、电表、燃气表（OOP 把每户人家整理得井井有条）；而水电燃气的管道是贯穿整栋楼的（AOP 处理这些”横穿”所有住户的公共设施）。

3. 底层基石：代理模式

AOP 能”不改业务代码就给方法加功能”，靠的不是魔法，而是动态代理。理解了代理，AOP 就懂了一大半。

3.1 什么是代理模式

代理模式是 23 种设计模式之一（结构型模式）。它的作用是：在调用目标方法时，不再直接调用目标对象，而是先经过一个”代理对象”，由代理去间接调用。

  • 代理（Proxy）：封装非核心逻辑的类/对象，负责”加料”。
  • 目标（Target）：被代理的类/对象，只负责核心业务。

生活中的代理：

  • 明星接广告要通过经纪人；
  • 老板谈合作要约时间要通过秘书；
  • 买房卖房要经过房产中介。

你没有直接见到明星本人（目标），而是通过经纪人在中间处理了一堆杂事（增强逻辑），明星只负责拍广告（核心业务）。

3.2 静态代理

生活小案例：你有一套房子要出租，嫌找租客、核验、签合同、收租太麻烦，于是专门招了一个固定中介，只服务你这一套房。所有对接都由他处理。

代码解释：

  1. 代理类和目标类实现同一个接口，外界感觉不到差别；
  2. 代理持有目标对象，在调用前后插入增强代码；
  3. 外界只接触代理，目标方法被”包”在里面。

静态代理的致命缺点：代理类写死了，一个目标类就要配一个代理类。如果 100 个 Service 都要加日志，就得写 100 个静态代理类——代码照样重复，照样难维护。

于是我们需要一个”通用的、能自动生成”的代理——动态代理。

3.3 动态代理

生活小案例：你不再找固定中介，而是直接联系房产平台（我爱我家、链家这类）。你不用管具体是谁来办事，平台会根据房源位置、租客需求、中介忙碌情况，动态给你匹配最合适的中介。具体的人由平台按需生成、动态分配——这就是动态代理。

动态代理的核心特点：不用手写代理类，程序运行时由 JVM 自动生成。

主流有两种实现：

3.3.1 JDK 动态代理（基于接口）

  • 依赖接口：目标类必须实现至少一个接口；
  • 核心 API：java.lang.reflect.Proxy（生成代理对象） + InvocationHandler（定义增强逻辑）；
  • 适用场景：目标类实现了业务接口（开发中最常见，比如各种 Service 接口）。

代码解释：

  1. Proxy.newProxyInstance(...) 在运行时”现场造”出一个代理类，它同样实现了 UserService 接口；
  2. 第三个参数是增强逻辑：所有对代理方法的调用，都会进到这段 lambda 里；
  3. method.invoke(target, argsArr) 才是真正去调用目标方法；
  4. 一个 InvocationHandler 可以套用到任意多个目标类，增强逻辑只写一次——这正是静态代理做不到的。

3.3.2 CGLIB 动态代理（基于继承）

  • 无需接口：直接继承目标类生成代理，目标类可以没有任何接口；
  • 核心 API：Enhancer（生成代理对象） + MethodInterceptor（定义增强逻辑）；
  • 适用场景：目标类没有实现任何接口。

一个真实会遇到的坑：在较新的 JDK 上跑 CGLIB 可能报错

原因：JDK 9 引入模块系统（JPMS）后对反射做了严格限制，CGLIB 想反射调用 ClassLoader.defineClass() 被拦住了。

3.3.3 两种动态代理对比

特性 JDK 动态代理 CGLIB 动态代理
依赖条件 目标类必须实现接口 目标类无需实现接口
实现方式 实现与目标类相同的接口 继承目标类
核心 API Proxy + InvocationHandler Enhancer + MethodInterceptor
生成速度 较快 较慢（要生成字节码）
调用性能 反射调用，略慢 直接调用，略快
Spring AOP 适配 有接口时默认使用 无接口时自动切换

4. AOP 九大核心术语

搞懂这些名词，看官方文档和面试就不慌了。

术语 英文 通俗解释
横切关注点 Cross-cutting Concern 从各方法中抽出来的同一类非核心逻辑（如”日志”就是一个横切关注点）。有几个附加功能就有几个横切关注点
通知 / 增强 Advice 每个横切关注点上要做的事，写成方法就是通知方法（如”打印日志”这个方法）
连接点 JoinPoint 可以被增强的”候选点”。Spring 中就是目标类的方法
切入点 Pointcut 从连接点中”选中”哪些来增强，用表达式描述（如 execution(* *..UserService.*(..))）
切面 Aspect 切入点 + 通知的结合，通常就是一个加了 @Aspect 的类
目标 Target 被代理的目标对象
代理 Proxy 对目标对象应用通知后创建的代理对象
织入 Weave 把通知应用到目标、生成代理对象的过程。Spring 选择运行期织入
引入 Introduction 在不修改类的前提下，动态给它添加新方法/新字段（进阶话题，了解即可）

用一句话串起来：

在连接点（所有方法）里，用切入点（表达式）挑出要增强的方法，把通知（增强逻辑）按织入（运行时生成代理）的方式加到目标上，得到代理；而切面就是”切入点 + 通知”的打包。

通知的 5 种类型（后面第 6 节详讲）：

  • 前置通知 @Before：目标方法执行前运行；
  • 返回通知 @AfterReturning：目标方法正常返回后运行（寿终正寝）；
  • 异常通知 @AfterThrowing：目标方法抛异常后运行（死于非命）；
  • 后置通知 @After：目标方法最终结束时运行（盖棺定论，不管正常还是异常）；
  • 环绕通知 @Around：用 try...catch...finally 包住整个目标方法，能覆盖上面全部位置。

Java 自带的动态代理用起来还是有点繁琐（要自己写 InvocationHandler）。Spring AOP 就是在动态代理基础上做的一层封装：我们只要写少量配置/注解，Spring 在背后替我们生成代理、织入逻辑。

补充：AspectJ 是更早、更完整的 AOP 实现框架，Spring AOP 借用了它的注解（如 @Aspect、@Before）和切入点表达式语法，但底层用的是自己的动态代理。

9. 环绕通知

环绕通知是功能最强的一种，它用 try...catch...finally 把目标方法整个包起来，能实现其它四种通知的所有效果。

9.1 语法要点

  • 用 @Around 声明；
  • 用 ProceedingJoinPoint 类型的形参获取目标方法细节；
  • 通过调用 proceedingJoinPoint.proceed() 触发目标方法；
  • 内部通常用 try...catch...finally 结构；
  • 一定要把目标方法的返回值返回出去（最容易漏！）。

10. 切面优先级 @Order

同一个目标方法上可能有多个切面。切面的优先级决定了它们的内外嵌套顺序：

  • 优先级高的切面在外层；
  • 优先级低的切面在内层。

用 @Order 控制：

实际意义：嵌套顺序会显著影响性能。例如”事务切面”和”缓存切面”同时存在——如果缓存能命中，就根本没必要开启事务。因此通常让缓存切面优先级更高（在外层），先查缓存，命中就直接返回，避免白白开启事务。

11. JDK 代理 vs CGLIB 代理

11.1 Spring 如何选择

  • 目标类有接口 → 默认用 JDK 动态代理；
  • 目标类没有接口 → 自动使用 CGLIB 动态代理。

Spring Boot 2.0 之后，spring.aop.proxy-target-class 默认值变成了 true，也就是默认强制使用 CGLIB 代理（即使目标类有接口也用 CGLIB）。

11.2 想强制用 JDK 代理怎么办

11.3 即使配置了 JDK，Spring 仍可能兜底用 CGLIB

目标类满足以下任一条件时，Spring 会”兜底”选择 CGLIB：

  • 目标类实现的是非 public 的内部接口；
  • 目标类本身已经是代理对象（例如循环依赖导致 Spring 提前为它生成了代理）；
  • 目标类包含 final 修饰的方法。

了解这些边界情况，有助于排查”为什么我明明配了 JDK 代理，实际却不是”的问题。

13. 常见坑与面试高频点

1. 自己调用自己的方法，切面不生效！

原因：通知靠代理对象生效，this.b() 绕过了代理。解决：注入自身 / 用 AopContext.currentProxy() 等。

2. 私有方法、final 方法无法被增强。

JDK 代理靠接口，CGLIB 靠继承——两者都拦不住 private / final / static 方法。

3. @AfterReturning 拿不到返回值？

检查 returning 指定的名字和形参名是否完全一致。

4. 环绕通知忘记 return 返回值 / 忘写 proceed()。

前者导致调用方拿到 null，后者导致目标方法根本不执行。

5. 切入点表达式的包名要写”目标类”的包名，不是接口的包名（尤其是在 execution(* ...service.UserService.*(..)) 里，注意区分类与接口的包路径）。

6. Spring AOP 只能增强 Spring 容器管理的 Bean。

自己 new 出来的对象不会被代理，通知自然不生效。

14. 全文总结

  1. AOP 是什么：OOP 的补充，用”横切”的方式抽取公共逻辑（日志、事务、权限、耗时统计……），在不改动业务代码的前提下动态增强方法。
  2. 底层是什么：动态代理（JDK 基于接口、CGLIB 基于继承）。静态代理太死板，动态代理才通用。
  3. 核心概念：横切关注点、通知、连接点、切入点、切面、目标、代理、织入。
  4. 怎么用：加 spring-boot-starter-aop 依赖 → 写目标类（纯净业务）→ 写切面类（@Aspect + @Component + 通知注解）→ 用时直接注入。
  5. 五种通知：@Before、@AfterReturning、@AfterThrowing、@After、@Around（最强，能包住全部）。
  6. 定位靠表达式：execution(修饰符 返回值 包.类.方法(参数))，善用 * 与 ..，并集中管理切入点。
  7. 优先级：@Order 数值越小越靠外层，嵌套顺序影响性能（如缓存应先于事务）。
  8. 代理选择：有接口默认 JDK，无接口用 CGLIB；Spring Boot 2.0+ 默认强制 CGLIB，可用 spring.aop.proxy-target-class=false 覆盖。
  9. 实战价值：像”方法耗时统计”这样的需求，一个切面就能完成，业务代码零侵入。

最后再记一次：AOP 让你把”到处都要写、和业务无关、内容雷同”的代码集中到一处管理，需要时自动加到目标方法上——业务归业务，杂活归切面。
