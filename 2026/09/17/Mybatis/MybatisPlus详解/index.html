MybatisPlus详解

一、什么是 MybatisPlus

MybatisPlus（简称 MP）是一款 MyBatis 的增强工具，在 MyBatis 的基础上只做增强不做改变，为简化开发、提高效率而生。它和 MyBatis 的关系就像”魂斗罗中的 1P 和 2P”——基友搭配，效率翻倍：MyBatis 负责灵活的 SQL 控制，MP 负责把重复的 CRUD 干掉。

MyBatis 的痛点 vs MP 的解法

痛点（原生 MyBatis） MybatisPlus 的解法
单表 CRUD 都要写 XML/SQL 内置通用 BaseMapper，继承即用
手写分页 SQL 或引入 PageHelper 内置物理分页插件，配置即用
动态条件拼接繁琐（<if> 标签） Wrapper 条件构造器，链式 API
实体字段与表列手动映射 约定大于配置 + 注解映射
主键策略、逻辑删除等通用能力缺失 注解 + 插件开箱即用
没有代码生成 内置代码生成器 / MyBatisX 插件

官方特性清单

特性 说明
无侵入 只做增强不做改变，引入它不会对现有工程产生影响
损耗小 启动即自动注入基本 CRUD，性能基本无损耗，直接面向对象操作
强大的 CRUD 内置通用 Mapper、通用 Service，少量配置实现单表大部分 CRUD
支持 Lambda 调用 通过 Lambda 表达式编写查询条件，无需担心字段写错
支持主键自动生成 多达 4 种主键策略（内含分布式 ID 生成器 Sequence）
支持 ActiveRecord 模式 实体类继承 Model 类即可直接进行 CRUD 操作
内置代码生成器 快速生成 Mapper、Model、Service、Controller 层代码
内置分页插件 基于 MyBatis 物理分页，写分页等同于普通 List 查询，支持 MySQL、Oracle、PostgreSQL 等多种数据库
内置性能分析插件 可输出 SQL 及执行时间，快速揪出慢查询
内置全局拦截插件 全表 delete/update 智能分析阻断，预防误操作

一句话总结：MP 把”单表操作”这件事做到了零 SQL，多表复杂查询仍然交给 MyBatis 原生方式。

三、核心注解详解

MP 的注解是实体类与数据库表之间的”映射桥梁”，核心解决 “实体属性 ↔ 数据库字段” 的匹配问题。

1. @TableName：实体类关联数据库表

属性 类型 说明
value String 声明实体类对应的数据库表名
schema String 指定数据库 schema（多租户/多 schema 场景，日常极少用）
  • 默认规则：类名与表名一致（忽略大小写）时可省略；
  • 常见场景：表名有统一前缀（如 t_、sys_）时必须指定；
  • 全局配置替代：所有表都有统一前缀时，可全局配置，避免每个实体都写注解：

2. @TableId：标识主键字段

属性 类型 说明
value String 主键对应的数据库字段名（默认：属性名转下划线）
type IdType 主键生成策略（默认跟随全局配置）

主键生成策略 IdType：

策略 含义 适用场景
AUTO 数据库自增（依赖表的主键自增配置） 单库单表、表配了 AUTO_INCREMENT
ASSIGN_ID MP 自动生成雪花算法 ID（Long 型） 分布式系统、无需数据库自增（默认策略）
ASSIGN_UUID MP 自动生成 UUID（String，无中划线） 字符串主键、需全局唯一
INPUT 程序中手动赋值 主键由业务自定义
NONE 无策略 跟随全局配置

全局统一主键策略：

3. @TableField：标识普通字段

属性 类型 说明
value String 属性对应的数据库字段名（默认：属性名转下划线）
exist boolean 标记属性是否对应数据库字段（false：仅实体类属性，无对应列）
fill FieldFill 字段自动填充策略（INSERT / INSERT_UPDATE / UPDATE）
select boolean 查询时是否查该字段（false：查询时忽略，适合大字段/敏感字段）

⚠️ exist=false 是高频坑：实体类中的临时属性（如关联查询结果、前端回显字段）必须标记 exist=false，否则 MP 会尝试匹配数据库字段，SQL 直接报”Unknown column”。

4. 其他常用注解

注解 作用
@TableLogic 逻辑删除字段（配合全局配置或 value/delval 属性）
@Version 乐观锁版本字段（需配合乐观锁插件）
@KeySequence Oracle 等序列主键，指定序列名

四、通用 Mapper 与通用 Service

1. BaseMapper（数据访问层）

BaseMapper 是 MP 提供的通用 Mapper 接口，封装了增、删、改、查等常用方法，自定义 Mapper 只需继承并指定实体泛型，无需编写任何基础 SQL。

核心方法速查：

方法 作用 关键说明
insert(T entity) 新增一条 主键自动回填到实体对象
deleteById(id) 按主键删除 配合 @TableLogic 变为逻辑删除
deleteBatchIds(idList) 按主键集合批量删除
deleteByMap(columnMap) 按多字段等值删除 key 必须是数据库字段名（如 user_name），不是属性名；只支持等值条件
delete(wrapper) 按条件删除 条件由 Wrapper 封装
updateById(T entity) 按主键更新 仅更新非 null 字段（entity 必须带主键）
update(T entity, Wrapper wrapper) 按条件更新 支持模糊、范围等复杂更新条件
selectById(id) 按主键查询 无数据返回 null
selectBatchIds(idList) 按主键集合批量查询
selectByMap(columnMap) 按多字段等值查询 同 deleteByMap，key 为数据库字段名
selectOne(wrapper) 按条件查一条 多条匹配会抛异常
selectList(wrapper) 按条件查列表 传 null 查全表
selectCount(wrapper) 按条件统计
exists(wrapper) 判断是否存在 返回 boolean
selectPage(page, wrapper) 分页查询 需配置分页插件

2. IService + ServiceImpl（业务逻辑层）

IService 是 MP 提供的通用 Service 接口，基于 BaseMapper 封装了更贴合业务层的操作，补充了批量操作、分页等能力，方法命名遵循 “get（查单行）、remove（删除）、list（查集合）、save（新增）、page（分页）” 规范。

核心方法速查：

方法 作用 关键说明
save(T entity) 新增一条 底层调 insert，命名更贴业务
saveBatch(Collection<T>) 批量插入 默认 1000 条一批，可自定义批次
saveOrUpdate(T) 有主键则更新，无则插入
removeById(id) 按主键删除
removeByMap(columnMap) 按多字段等值删除
remove(wrapper) 按条件删除
updateById(T) 按主键更新
updateBatchById(Collection<T>) 按主键批量更新 底层分批执行，默认 1000 条/批
getById(id) 按主键查单条
getOne(wrapper) 按条件查一条
list() / list(wrapper) 查集合
count(wrapper) 统计
page(page) / page(page, wrapper) 分页查询 补充 Mapper 层分页能力

3. BaseMapper vs IService 对比总结

维度 BaseMapper IService
定位 数据访问层（DAO/Mapper） 业务逻辑层（Service）
底层依赖 直接对接 MyBatis 生成 SQL 基于 Mapper 封装，调用 Mapper 实现
方法风格 偏数据库语义（insert/delete/select） 偏业务语义（save/remove/get/list/page）
功能侧重 基础单表 CRUD 补充批量、分页等高级能力
使用场景 简单 CRUD、自定义复杂 SQL 时 业务层开发（批量操作、分页查询）

结论：Mapper 只需继承 BaseMapper，业务逻辑统一走 Service 层；saveBatch 底层是 JDBC batch，MySQL 连接串建议加 rewriteBatchedStatements=true 才能真正提速。

五、条件构造器 Wrapper（重点）

Wrapper 是 MP 封装查询/更新条件的通用抽象接口，核心价值：无需手动拼接 SQL 片段，通过链式调用构建复杂条件。常用实现：

  • QueryWrapper / LambdaQueryWrapper：查询条件
  • UpdateWrapper / LambdaUpdateWrapper：更新 SET 子句 + WHERE 条件

1. QueryWrapper：查询条件构造器

常用条件方法：eq(=)、ne(!=)、gt(>)、ge(>=)、lt(<)、le(<=)、between、notBetween、like('%xx%')、likeLeft('%xx')、likeRight('xx%')、in、notIn、isNull、isNotNull、orderByAsc/Desc、groupBy、having。

2. UpdateWrapper：更新条件构造器

核心独有能力：支持将字段值设为 null（实体对象更新时非 null 字段才会参与更新，无法实现置 null）。

3. Lambda 系列（生产环境首选）

普通 Wrapper 用字符串指定字段名，拼写错误只能运行时暴露；Lambda 系列通过方法引用实体属性，编译期即可校验，IDE 自动补全、重构安全。

六、逻辑删除

逻辑删除（假删除）：不物理删除记录，仅把”是否删除”标记字段改为已删除状态（如 deleted=1），数据仍保留在库中便于恢复和分析；查询时自动过滤已删除数据。

方式 行为 数据是否可见
物理删除 真实执行 DELETE，记录从库中移除 不可见，无法恢复
逻辑删除 执行 UPDATE，标记字段改为”已删除” MP 查询自动过滤，库中仍保留

4. 注意事项

  1. 字段类型：deleted 为 INT 时实体属性用 Integer，不要用 Boolean，避免类型转换异常；
  2. 查询已删除数据：通用方法查不到已删数据，需要时手动拼条件 wrapper.eq("deleted", 1)；
  3. 只对通用方法生效：逻辑删除只改写 MP 的通用 CRUD，自定义 SQL 需手动处理 deleted 条件；
  4. 唯一索引冲突：逻辑删除后唯一键会失效（同一邮箱”删除后重新注册”撞唯一键），常见解法：唯一列改为 email + deleted 联合唯一，或删除时把 email 改写为 CONCAT(email, '_del_', id)。

八、实战：基于 MP 改造用户模块

以一个典型三层用户模块为例，展示 MP 化改造后各层的最终形态。

1. Mapper 层：删掉 XML 和自定义方法

2. Service 层：继承 IService，业务方法只剩核心逻辑

3. Controller 层：只做参数校验和响应封装

改造收益：Mapper 层 XML 全部删除、Service 层只剩业务语义代码、动态查询从”XML <if> 标签”变成”condition 参数”，代码量减少 60% 以上。

十、代码生成

1. MyBatisX 插件（IDEA 可视化生成）

MyBatisX 是 MP 官方的 IDEA 插件，可根据数据库表快速生成 Entity、Mapper、Mapper.xml、Service、ServiceImpl 等全套代码，使用步骤：

  1. 安装插件：IDEA 插件市场搜索 MyBatisX 在线安装；
  2. 配置数据库连接：在 IDEA 的 Database 面板中配置好数据源；
  3. 生成代码：右键目标表 → MybatisX-Generator，依次配置实体类信息（包名、父类等）和代码模板信息，点击 Finish 即可生成全套骨架代码。

十一、常见坑与最佳实践

# 问题/坑 正确做法
1 同时引入 MyBatis starter 与 MP starter 只引 MP starter，避免 SqlSessionFactory 冲突
2 实体加了非表字段报”Unknown column” 加 @TableField(exist = false)
3 分页不生效（不报错但查出了全表） 必须注册 MybatisPlusInterceptor + 分页插件
4 @Version 乐观锁不生效 注册乐观锁插件；更新前先 select 保证 version 有值
5 saveBatch 很慢 JDBC 连接串加 rewriteBatchedStatements=true
6 updateById 传 null 字段被忽略（默认不更新 null） 需要更新为 null 时必须用 UpdateWrapper.set()
7 逻辑删除后唯一索引冲突 唯一键设计加入 deleted，或删除时改写唯一列值
8 全表 update/delete 误操作 加 BlockAttackInnerInterceptor 拦截
9 deleteByMap/selectByMap 查不到数据 key 必须是数据库字段名（下划线），不是实体属性名
10 大数据量 selectList 撑爆内存 用 selectPage 或 ResultHandler 流式查询

架构层面的建议：

  1. 单表用 MP 内置方法，多表/复杂 SQL 走 MyBatis 原生——不要为了”纯 MP”硬拼 Wrapper 写出难维护的 SQL；
  2. 全局配置统一收敛到 yml（主键策略、逻辑删除、表前缀），避免到处写注解；
  3. 拦截器顺序：多租户/数据权限 → 防全表攻击 → 乐观锁 → 分页；
  4. Service 层继承 ServiceImpl，批量操作直接享受 saveBatch / updateBatchById / removeBatchByIds；
  5. 逻辑删除只对通用方法生效，自定义 SQL 记得手动带 deleted=0 条件。

十二、小结

层次 你需要写的代码 MP 帮你做的事
实体 一个 POJO + 少量注解 字段映射、主键策略、逻辑删除、自动填充
Mapper extends BaseMapper<T> 全部单表 CRUD + 分页 SQL
Service extends ServiceImpl 批量操作、saveOrUpdate、语义化命名
查询条件 链式 Lambda Wrapper 动态拼 WHERE，替代 <if> 标签
复杂查询 照常写 XML 与 Wrapper/分页/逻辑删除兼容

MP 的定位很清晰：把 80% 的重复性数据访问代码（单表 CRUD、分页、逻辑删除、乐观锁）自动化掉，把剩下 20% 的复杂 SQL 的控制权完整留给你。 掌握 BaseMapper、LambdaWrapper、分页插件三件套，就能覆盖日常 90% 的开发场景。
